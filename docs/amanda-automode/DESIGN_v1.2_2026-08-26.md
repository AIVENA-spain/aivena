## 1. The brain

- **Core:** claude-sonnet-5 agentic tool loop per turn (not single-shot drafting). Model IDs live in per-role env config (`MODEL_ID_CONVERSATION`, `MODEL_ID_VERIFIER`) — changing one requires a golden-suite run.
- **Context (3-layer memory, not "full history"):** (1) last ~20 turns verbatim; (2) a persistent **structured lead-state object** — timestamped, supersession-aware (latest value wins): budget, areas, must-haves, **rejected properties**, promised follow-ups — promoted from the existing interest-extraction trigger and declared authoritative over old raw messages; (3) an episodic summary of older history refreshed asynchronously. Caps tokens deterministically; prevents "not listening" (re-pitching rejected property / quoting stale budget).
- **Tools** (server-side, agency-scoped; agency_id/lead_id/conversation_id always derived from the conversation row, never model-supplied): search_properties · get_property_details · get_lead_profile · get_area_info (precomputed locality guides; web_search max_uses=1 as logged fallback only) · propose_viewing_slots · book_viewing · reschedule_viewing · cancel_viewing · handoff_to_human · **cannot_answer(reason)** — abstention as a first-class tool, so "I don't know" is trained behavior, not prose.
- **Media (P0, not an afterthought):** voice notes transcribed (STT) and injected as `[voice note]` turns; images get a vision one-line description (matching answered from catalogue search on it, never invented similarity); location pins parsed; unsupported media → graceful acknowledgment + handoff if decision-relevant. Audit the inbound EF's media storage during the repo-capture step. Red-team probe: "voice note containing a cancellation."
- **Language:** reply in the lead's language (13 supported), persisted; per-language affirmative/negative lexicons live in the eval fixtures.

## 2. Grounding & gates (rebuilt for chat, not bolted from web-Amanda)

- **Turn classifier first** (deterministic): classify the draft into claim classes — property-fact / scheduling-fact / area / social-phatic. Numeric guard only on catalogue-mapped numbers; the independent verifier only on extracted fact-bearing claims (structured, not prose); **social/acknowledgment turns bypass the verifier** — so the bot is never evasive about "see you Saturday!".
- **On a gate miss:** ONE constrained regeneration ("rewrite without claim X") before any fallback; handoff only if regeneration also fails. **False-block budget:** <2% of social turns blocked = P2 promotion criterion.
- **Staleness guard** (new, deterministic): properties untouched for N days (default 45) → hedge on price/availability ("let me confirm the current price with the office") or escalate; digest surfaces stale listings Amanda used, with one-tap confirm/refresh.
- **No-commitment floor** (deterministic): never "reserved", never availability guarantees beyond "listed as available today", prices always as-listed framing; booking a VIEWING is the only commitment-class action, ever.

## 3. Escalation — Amanda keeps the conversation; agents become her back-office

**(Christian's pattern, locked 2026-08-26 — supersedes "sensitive question ⇒ human takes over the thread" as the default.)** The client keeps ONE conversational partner: Amanda. Three rungs, in order of preference:

**3a. ANSWER (the floor).** Informational acts answered directly per §2: asking price stated as-listed; general mortgage landscape with a broker-referral rider; everything grounded.

**3b. ASK-THE-AGENCY — the `ask_agency` loop (default for agency-answerable questions).** When the client asks something only the agency can decide/confirm — "is the price negotiable?", commission, furniture included, viewing-hours exception, availability confirmation:
1. Amanda tells the client she'll **ask the agency that specific question and come back to them** — then immediately **keeps the conversation alive**: more Q&A on this property, offers to find other matching properties, and **natural client-intel gathering** (timeline, budget shape, must-haves, situation) woven into casual/property chat — helpful conversation, never an interrogation; everything lands in the lead-state (§1 memory).
2. `ask_agency(question, context)` writes a **question ticket** — new dashboard task type `amanda_question` {conversation, lead, property, clean AI-phrased question} — surfaced in the dashboard tied to the client with a **one-box reply field**; rides the same realtime + escalation-phone push as handoffs; SLA timer + aging re-alerts.
3. Agent types the answer → engine event fires → **Amanda relays it the moment it lands**, in the client's language, **with attribution** ("I checked with the office — they say…"). The relay is the AGENCY'S words (agency-authored = agency-knowledge trust layer, still scrubbed); attribution also defuses bot-binds-the-agency liability.
4. **Window law applies to the relay:** if the 24h window closed while waiting, the relay goes via an approved utility template ("we have an update on your question — reply to continue") — this template joins the 13-language template-coverage audit NOW.
5. **SLA honesty:** unanswered past the per-agency deadline → Amanda proactively updates the client with working-hours-aware copy ("the office opens at 9:30 — I'll come straight back to you"); the ticket ages/escalates; it never silently dies.
6. **Knowledge flywheel:** when an agent answers, one tap offers "save as Amanda knowledge" (through the §5 save-time screen) — recurring questions stop needing tickets.

**Mode-aware degradation (tool layer, not prompt):** FULL-AUTO = the loop runs end-to-end. ASSISTED = same (conversational auto-replies are permitted; bookings stay one-tap). APPROVAL-FIRST/SHADOW = the "I'll ask the office" reply and the relay are drafts the agent approves; the ticket is still created for real (internal write, sends nothing).

- **Channel = WhatsApp itself (the headline finding).** The ticket notification is sent AS A WHATSAPP MESSAGE to the agent's phone from a **dedicated "AIVENA Office" sender** (second number on the existing WABA — never the buyer-facing number, so staff replies can never race the lead pipeline; the `agency_staff_numbers` router branch stays as defense-in-depth: a staff From-number hard-stops the lead pipeline, never creates a lead, never wakes Amanda-the-seller). ## 4. Transactional integrity (the "must not fail" machinery)

- **Slots:** Postgres **EXCLUDE (gist) constraint** on active viewings (agency/agent × time-range) = the arbiter; app-level checks are advisory. Slot-hold rows (TTL ~15 min) at proposal time. Constraint violation → "that slot was just taken — here are alternatives."
- **Confirmation:** a **pending_action table** {action, property, slot tstzrange, expires_at}; book executes only when exactly ONE unexpired pending action exists, the inbound affirms it, and no newer inbound modifies it; multiple/expired/unclear → re-ask, never guess. Prefer WhatsApp interactive reply buttons (postback = pending_action_id) over text-parsing "vale".
- **Dates:** the model NEVER emits absolute datetimes from relative phrases. A deterministic resolver (agency IANA tz, fresh now() each turn) converts; ambiguity → clarify; every proposal echoes the explicit form ("Friday 30 August, 17:00") in the lead's language; pending_action stores tstzrange.
- **Idempotency end-to-end:** turn_id = f(conversation, MessageSid); outbound-intent rows (unique) before Twilio; book_viewing takes idempotency_key = pending_action_id; durable turn journal of tool effects for replay-after-crash.
- **Inbound processing = outbox pattern**, not fire-and-forget webhook: EF writes a queue row in the same transaction as the message; engine consumes the queue (ordering + retry for free); sweep alerts on unprocessed inbound >X min.
- **Locks & ordering:** Postgres lease per conversation (TTL + heartbeat, stealable with state re-read); debounce (12s adaptive, cap ~25s) so bursts become one turn; new inbound mid-loop → abort before side-effects, fold in, restart; booking transactions verify the inbound snapshot hasn't advanced. Cross-channel (web-Amanda + WA same lead): pending/holds keyed by lead_id, lead-level advisory lock on booking, cross-channel context note; identity linking on verified phone only.
- **Final send gate is atomic and total:** whatsapp-send-execute re-checks at the moment of send — 24h window (with 60–120s safety margin; near-boundary → template or park), opt-out, kill switch, **ai-muted/human-claimed**, and **ai_disclosure_sent_at** — refusing anything that fails. In-flight turns whose send is refused discard output, never retry. (Same pattern that already made opt-out safe.)
- **Mode enforced in the tool layer, not the prompt:** SHADOW = booking/handoff tools return simulated "would have done X" results (zero writes outside conversation/telemetry — enforced by test); ASSISTED = booking tools return "queued for one-tap approval"; FULL = validator-gated execution.
- **Degradation:** circuit breaker on model errors → agency auto-downgrades to APPROVAL-FIRST + alert + pre-written holding message (no model involved); all gates fail CLOSED (verifier down = hold for human); per-gate timeouts.
- **Mid-conversation agency edits:** property/viewing writes expire matching pending_actions and enqueue an engine event so Amanda proactively updates the lead; update/cancel RPCs gain expected-version args.

## 10. Tone & pacing doctrine — "never far from a human, never pushy" (Christian, 2026-08-26)

Christian's spec verbatim: buyer must *"never feel like theyre far away from a human"*, chat *"not too pushy… warm and helpful but not always writing long messages, just sometimes when she sees that the client is losing interest"*. Enforcement split is explicit: **the prompt is aspiration; the validators are law** — voice/warmth/mirroring guidance lives in the system prompt, but everything Christian actually fears is enforced deterministically in the send path (the model can draft anything; nothing pushy can leave).

- **Length law (linter-enforced):** default ≤3 sentences / ≤35 words, one idea per bubble; target band mirrors the buyer's own rolling median length (0.7–1.5×) and register (tú/usted, emoji, formality). Long-form (≤120 words, ideally split into two bubbles) ONLY when: buyer asked a broad open question · the one re-engagement message · a requested property summary · an office-answer relay needing context. Never two long messages in a row.
- **Question discipline:** max ONE interrogative sentence per message; after two consecutive answered questions the next message is statement-only. Intel slots (budget, timeline, financing, purpose, situation) fill as a **slow drip across the conversation** — one natural follow-up only when contextually earned; a filled slot is never re-asked (deterministic blocker); multi-slot enumeration is a banned form. This is how "as much client intel as possible, as naturally as possible" is achieved without ever feeling like a form.
- **Disengagement state machine (deterministic score, per turn):** reply-gap >3× the buyer's own median AND >8h · brevity collapse (2 replies ≤3 words after a longer baseline) · per-language closure tokens ("ok", "vale", thumbs-up-only) · declined suggestion with no counter-ask → lead_state flips active → **cooling**.
- **Re-engagement:** cooling triggers exactly ONE nudge, ≥24h after the buyer's last message, daytime send, and only with a **concrete value payload from a whitelist** (new matching listing, price change, new photos, an answer to a stated interest) — no payload, no nudge (wait up to 7 days for one). No reply in 5–7 days → one graceful sign-off ("I'll leave you in peace — I'm here whenever you like") → **dormant**, all proactive contact stops. **Lifetime cap: 2 value-nudges per conversation EVER**, counted in lead_state, enforced by the scheduler. (Consented property-alerts are a separate opt-in stream, ≤1/week.)
- **Pushiness guardrails in the send path:** scheduler refuses uninvited messages within 20 min of Amanda's last outbound (exceptions: delivering the promised office answer, corrections, finishing a split message); rejected_property_ids filters every suggestion; banned-pattern screen for urgency/scarcity/guilt ("last chance", "won't last", "many interested buyers", "you haven't replied", fake deadlines) — **LLM-judge tier, not 13-language regex** (reviewer: a regex lexicon across 13 languages is unmaintainable false confidence; small regex core for ES/EN + judge for the rest) — fail → regenerate, 2 retries → human queue.
- **Human proximity:** Amanda references the real office truthfully ("I'll check with the office", "María can show it Saturday" — real names, real facts only), hands over to a named agent, never claims to be human, never denies being an AI when asked; 20–90s jittered send pacing scaled to reply length — never an instant wall of text.
- **Golden-suite tone scenarios (added to §7):** silent buyer → exactly one payload nudge then silence · "ok"-only buyer → messages shorten, questions stop · rejected property never reappears (50-turn fuzz) · two-question draft rejected+regenerated · adversarial urgency injection blocked · 22:00 ticket → closed-office line, no night wait-update.
